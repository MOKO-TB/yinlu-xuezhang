> 本文所有"现状"**都是当场量出来的**，不是印象；量法与复量命令写在 §附。

## 一、用户想要的是什么

截图那张「发现新版本 v0.9.177」的卡，红笔圈住的是进度条那行：

> 下载中 0% · 0.0 MB / **878.0 MB**(几百 MB,可以最小化,别关窗口)

他的原话是"感觉是重新下一遍最新版本的，而不是更新新的内容"。**这个直觉是对的**，
而且他低估了严重程度 —— 见 §二。

一句话产品主张：**更新流量应当正比于"这次改了多少"，而不是正比于"这个产品多大"。**
现在的形状是后者，而且没有任何一处代码在试图做前者。

## 二、容量实测（先把"该不该做"钉死，再谈怎么做）

对 `dist/引路学长-0.9.177-win64.zip`（压缩后 **1,211,787,905 B = 1.13 GiB**，5122 条，
逐条归位后合计与总数相等）按层分桶：

| 层 | 内容 | 压缩后 | 占比 | 条目数 |
|---|---|---:|---:|---:|
| **L3** | 馆藏库 `crawled/`（`library.db` 等） | 699,260,035 | **57.70%** | **4** |
| **L3** | 浏览器内核 `ms-playwright/` | 321,080,866 | **26.50%** | 623 |
| **L2** | 第三方运行时（`_internal/` 其余） | 136,642,234 | 11.28% | 4415 |
| **L1** | 两个主程序 exe（内含 PYZ） | 47,267,011 | 3.90% | 2 |
| **L1** | 前端 `_internal/frontend/` | 7,487,382 | 0.62% | 77 |
| **L1** | 《使用说明》 | 50,377 | 0.00% | 1 |

**L3 数据+内核 = 84.2%；L1 我们自己的东西 = 4.5%。**

### Inno 口径：不是推算，是**编了三件变体实测**的（§八-3 已办）

上面那句"setup 里 L3 约占 0.70 GiB"原本是按未压缩占比推的。现在用本机
`ISCC.exe` 编了三件变体（**与 `packaging/gcode.iss` 逐字同参**：`Compression=lzma2/max` +
`SolidCompression=yes`，只差 [Files] 少收哪几块），量的是安装包**真实字节**：

| 变体 | 真实字节 | 占整包 | 这一档减下来的边际 |
|---|---:|---:|---|
| 整包（现状，就是发出去的那件） | 920,614,741 | 100% | — |
| 减掉浏览器内核 | 691,614,585 | 75.1% | 内核 **229,000,156 B = 24.9%** |
| 再减掉馆藏库（= 仅 app） | **141,962,981** | **15.4%** | 馆藏库 **549,651,604 B = 59.7%** |
| 只装 L1（两个 exe + 前端 + 手册） | 56,481,112 | 6.1% | L2 运行时 85,481,869 B = 9.3% |

⚠ **口径要说准**：实心压缩（solid）下"减去一块得到的差"不等于那块单独压缩的大小，
它是"在这一棵树的上下文里这块贡献了多少"。所以这四个数是**决策用的边际**，
不是四块内容的独立体积之和（相加会比整包略大）。

**两条直接结论：**
1. **路 1 的收益从"约 0.70 GiB"变成实测的 878 MiB → 135 MiB（15.4%）**，
   而且拆得很干净：**馆藏库 59.7% + 内核 24.9%** —— 两者节奏不同（内核只在升级
   playwright 时变），所以"各自 stamp、各自可跳过"这条设计要求在数据上是对的：
   只做馆藏库那一件的外置，就已经砍掉**六成**。
2. **路 2b 的价值也被量出来了**：容器不动的前提下，一轮纯代码改动的下限是
   **54 MiB**（`l1only` 那件），而真实变化是 2.4 MB = **整包的 0.267%**。
   也就是说 54 MiB 里有 ~51 MB 是"被 24 MB 的 exe 容器拖着重下"的部分。

再用 PyInstaller 自己的归档读取器从 exe 里把 PYZ 抠出来量（不是估）：

- `minicode.*` 在 PYZ 里 = **1,757,609 B = 1.68 MiB，127 个模块**；
- 前端本体 `index.html` = **697,973 B**；
- 第三方纯 Python 在 PYZ 里 = 20.66 MiB（**不是我们改的**）。

**⇒ 这一轮真正变化的东西 ≈ 2.4 MB，用户付的流量是 878 MB。比值约 375 倍。**

### ⚠ 一个我上一轮没看到、这一轮量出来的硬约束

那 1.68 MiB 的代码**被封在一个 24,078,405 B 的 exe 里**（PYZ 是单个归档，改一行整块变），
这样的 exe 有两个。所以：

**"逐件替换"的下限不是 2 MB，而是 ~55 MB**（两个 exe 47 MB + 前端 7.5 MB）——
因为"可替换单元"就是这两个整体。**不拆这个容器，任何 manifest 方案都到不了 2 MB 级。**

## 三、已经具备的（别重做）

这一格**不需要新写一个下载器**。v0.9.177 里这些已经是真的（`minicode/proactive.py`）：

- **断点续传**：`Range: bytes=N-` + `If-Range`，半截配一张 `.part.meta` 侧记；服务器不认
  Range 就从 0 重写；取消/中断**留着**半截（`pending_part()` 让重启后还看得见）；
- **整文件 sha256 校验**，对不上就删（坏前提不留）；拿不到清单就标 `verified=none` 并且不给装；
- **两条直链**：资产 API 优先、`browser_download_url` 兜底；**证书两跳**四条路共用一份底座；
- **旧件清理**：`prune_updates()` 只认这条通道自己写下的文件名形状；`updates/` 已进「我的数据」；
- **馆藏库已经有 stamp**（`library.db.stamp.json`，`minicode/library.py:13`）—— 里面**已经记了
  size / count / sha256**，`scripts/check_library_db.py` 就是拿它做完整性核对的。
  所以路 1 的"这件要不要下"**不需要新造一套格式**，只要把这份凭证升成"发布端也带一份、
  两边一比"。**锚点已经存在一半**，这是路 1 便宜的实际原因。

所以这一格要改的是**"下载什么"**，不是"怎么下载"。

## 四、真正的缺口（四条路，按风险从低到高）

### 路 1 · 三件资产各自版本化（低风险，收益 84%）

发布端从"一件 setup"变成**三件各自带版本**：`app`（L1+L2）/ `library`（L3 馆藏）/
`browser-kernel`（L3 内核）。更新时逐件比对本地 stamp，**对得上的那件一个字节都不下**。

- 不需要差分、不需要基线信任：数据文件要么在要么不在，stamp 说话；
- 形状也合适：馆藏库只有 **4 个文件**、内核 623 个，都是"整件替换"极友好的单元；
- 两者节奏不同（内核只在升级 playwright 时变，馆藏按爬取节奏变）→ **必须各自 stamp**，
  合成一件就浪费；
- 收益（**Inno 口径实测**，见 §二那张表）：整包 878 MiB → **135 MiB**，即 **15.4%**；
  其中馆藏库一件就占 59.7%、内核占 24.9% —— **只做馆藏库外置就已经砍掉六成**。
- ⚠ 代价要说清：这需要**构建端多产出一件"仅 app"的包**，不是"更新时少读几个字段"就完事。

### 路 2 · manifest + updater（中风险，是承载机制）

发布带一份 `manifest.json`：安装树里每个稳定件的名字 + sha256 + size + 一个**删除清单**。
更新包只含"哈希对不上的件 + 新增件"。应用时逐件哈希本机（只哈希 manifest 列的那些），
对上的跳过、对不上的替换、缺的补、**该删的删**，收尾整棵复验；旧件先移到回滚目录。
Windows 锁用极小的独立 updater 或"下次启动先替换再拉起"解决。VS Code / Chrome 的 updater
就是这个形状 —— **manifest + 整件替换，不发明二进制差分**。

上限：**54 MiB**（`l1only` 那件实测 —— 两个 exe + 前端 + 手册，受 §二的容器约束）。
**它的价值是"把路 1 的三件变成任意多件"，
不是它自己省流量。**

### 路 2b · 把 `minicode` 拆出 PYZ（中高风险，收益才到 2 MB 级）

让我们的代码住在**自己的可替换归档**里（如 `_internal/minicode.zip`，启动时挂进 `sys.path`），
于是"改一行"的变化量真的等于那一行所在的模块。收益：~55 MB → **约 2–4 MB**。

⚠ **硬前置，不是收尾工作**：`scripts/check_frozen_version.py` 现在靠"打开 exe → 定位 PYZ →
从 PYZ 取 `minicode.*`"核冻结针。代码一旦不在 PYZ 里，**这套包内验证会静默失明** ——
而它是本项目防"包里跑的不是这棵树"的唯一手段。所以顺序必须是：
**先给冻结验证备好新读法（双读过渡：既读 PYZ 也读 minicode.zip），再切容器。**

### 路 3 · bsdiff / zstd 整包二进制差分 —— **不做**

理由写死：① 输入已是压缩流，差分结果**不压缩**，省不了多少；② 基线错一个字节就是装坏，
而"验基线"的代价≈重下一遍；③ 多一套格式、多一套失败模式，收益却比路 1+2b 小一个量级。
做增量做得舒服的是 asar / 小文件树那种布局，不是 PyInstaller 单归档。→ 进 §六"刻意不做"。

## 五、必须写死的口径（不许做假）

1. **信任锚不变**：校验清单仍从 `api.github.com` 取（本轮刚修好它跟 302）。镜像只换**运输**，
   不换**信任**；哈希对不上照旧删。
2. **增量比整包更需要逐件哈希** —— "部分替换"出错比"整包重装"出错**更难察觉**，
   而更难察觉的坏法正是这个仓库反复清退的那一类。
3. **增量的最小单位是 manifest 差异（增 + 改 + 删），不是"新增"**。只下新增会在安装树里
   留下旧版死 `.pyd` 与旧前端，行为由"新旧混合"决定，没人说得清哪件在生效 ——
   **那比整包重装更危险**。这条不写进实现，做出来的就是一个会留尸体的更新器。
4. **基线不可信就退回整包，并且明说退回了** —— 静默降级成"其实下了 878 MB"是这一格最坏的
   一种骗人方式。
5. **两次点击不变**：下载一次、应用一次。不静默升级、不自己重启（与 v0.9.176 那条同口径）。
6. **单文件版没有文件树**：它只能走路 1（数据外置）或维持整件。三种形态（装机 / 免安装 zip /
   单文件）要分别在界面上说清"你这台这次能省多少"，不许用一句"增量更新"糊过去。
7. **卡上的数字要实测得到**：写"这次要下 X MB，其中馆藏库 Y MB 你机器上已有、本次跳过"，
   不写"增量更新"这种没有数的词。省了多少必须看得见，否则用户无法判断它有没有生效。

## 六、刻意不做 / 不要这样做

- **路 3 二进制差分**（理由见 §四）。
- **运行中替换文件**：Windows 锁着正在跑的 exe/.pyd，硬做要"重启后应用 + 回滚"，那是另一套子系统。
- **不询问的后台预下载**：违背两次点击；也违背"一次网络回答不该获得改这台机器的权力"。
- **自建对象存储 / 商业 CDN 当主源**：本地优先的立场下，多一个第三方依赖要单独拍板，
  不能当成"顺手加个镜像"。
- **为省流量把 onnxruntime / numpy 改成按需下载**：那是把"开箱即用"换成另一种坏法
  （第一次用到才下，且失败时用户不知道为什么功能不在了），收益远小于路 1。
- **不删用户机器上的馆藏库来省空间**：路 1 是"不再重下"，不是"少存一份"。

## 七、代价与验证口径（四项税）

|---|---|---|

## 八、要用户拍的板（三件事）

1. **做到哪一档就停？**
   - **A. 只做路 1**（878 MB → 约 160–190 MB，省 84%）；
   - B. 路 1 + 路 2（→ ~55 MB，省 94%）；
   - C. 路 1 + 路 2 + 路 2b（→ 2–4 MB，省 99.6%）。

   **推荐 A 先单独一轮。** 理由：路 1 不新增任何信任面就能吃掉 84%，而 B/C 的 manifest
   要等"可替换单元"定下来才建 —— 先建就会跟着容器改两遍。**收益的 84% 在最便宜那一档。**

2. **首装口径怎么改？**
   - **推荐：首装仍发完整包（保住"开箱即用"），发布时多产出一件"仅 app"包供更新用**；
   - 备选：首装也拆两件（每件都小，但新用户要下两次、且第一次启动可能面对"馆藏还没好"）；
   - 明确不选：只改更新逻辑不产新包 —— 那省不了任何字节，因为现在**只有**整包可下。

3. ~~**要不要先把 setup.exe 的精确占比量出来再动手？**~~ **已办（2026-10-16）**：
   没有"解包"（本机 `7zr` 精简版不带 Inno 处理器），改成**编三件变体实测**——
   用同一份 `lzma2/max` + 实心压缩参数，只差 [Files] 少收哪几块，得到 §二那张表。
   发布说明里那句"从 878 MB 降到 X MB"现在有了 X = **135 MiB**（路 1 之后），
   不是按比例推的。

## 九、落地偏差（v0.9.178 实施后补；读代码前先读这一节）

上面那份方案是"动手前写的"，实现时有十一处与本文不一致或本文没料到的，逐条记：

1. **"三件资产"实际落成了"两件安装包 + 一份清单"** —— 这是最大的一处缩水，必须说白：
   本文 §四·路 1 写的是"更新时逐件比对本地 stamp，对得上的那件一个字节都不下"。
   前半句按原样做了（对得上的确实一个字节都不下 —— **但这句话要等 v0.9.178 这一炉的
   包内探针复验通过才成立**：写这一版时它正因为第 9 条那个漂移而一次都没生效过，
   源码态无从判断）；
   **后半句没做**：馆藏库或内核**变了**的时候，不是"单独下那两件数据"，而是**退回整包**。
   理由是不想在没有 updater 的情况下发明"数据件原地替换"（那需要"替换中断电"的处理与
   回滚位，属于路 2 的机制）。所以今天的效果是：**数据不变的那一版省 84.6%，
   数据变了的那一版一分不省**。这条差异写进 `HANDOFF.md` §6 第 80 条①。
2. **多了一档方案里没有的判定**：清单说"可以下小件"、Release 里**却没有那件**
   （清单与资产表不一致）。不处理的话表现是"告诉用户跳过了 743 MB，实际下了 878 MB" ——
   两处各说各话，比不跳过更伤信任。所以 `plan_update` 是**五档**而不是本文列的四档，
   且这一档在 `check_update` 里兜了一层（退回整包 + 把矛盾写在句子里）。
3. **身份比对必须剔掉时间字段**：`library.db.stamp.json` 里有 `built_at`，每次构建都变。
   按整个 dict 比会导致**永远不一致**、跳过永远不生效。实现投影成 `{size,count,sha256}`
   与 `{files,bytes,digest}` 两组字段，并有一支针钉"`built_at` 不许进身份比对"。
   本文 §四 只写了"stamp 说话"，没写这一层。⚠ **这一条当时只做对了一半**（剔了时间字段，
   但两侧各写一份投影），实际破法见下面第 9 条。
4. **内核身份不能按目录字节流哈希**（本文 §四 也没写）：拷贝一次时间戳就全变，
   同一份内核在两次构建里会得到两个身份 → 永远跳不过。实现为「相对路径|每文件 sha256」
   排序后再摘要，身份只由内容与名字决定。
5. **少列了一项登记税**：`prune_updates()` 那道文件名形状闸不认识
   `app-setup.exe` 与 `assets.json`。漏了不会报错，表现是"用户按了清理、腾出 0 字节，
   而盘上躺着三件旧的小包"。已补进正则并加一支针专门钉"新产物有没有交登记税"。
6. **发布端"缺一件"的策略**：本文没写。实现成**有就必带、缺一件就打印为什么这一版不会
   跳过**，而不是硬失败 —— 但 `app-setup` 与 `assets.json` **必须同时在场**：只传清单不传
   小包，App 会走上面第 2 条那一档退回整包（能工作）；只传小包不传清单，那件包**永远不会
   被选中**（白占 135 MB 的下载位）。
7. **板②按推荐档执行**：首装仍发完整包，发布时多产一件"仅 app"包供更新用。
8. **两处数字被实测替换**：路 2 的下限从本文原写的"~55 MB"改成**实测 54 MiB**
   （编变体量出来的，见 §二）；板③（要不要解包 setup.exe 精确量）已办，
   且**没有解包** —— 本机 `7zr` 精简版读不了 Inno，改成用同一份压缩参数编变体。

9. **上面第 3 条那份"投影"最初是两侧各写一份，因而当场破了路 1** —— 构建端
   （`scripts/build_exe.py::assets_manifest`）写清单时整份抄凭证、多带一个 `schema`，
   App 端（`minicode/proactive.py::local_identities`）只取三个字段，而 `_same_identity`
   按"要比对的全部键"逐项比：差一个键就永远判"不一致"。**结果是这一格在源码态

   同一套字段写的，两侧一致是**假设**一致而不是**代码**一致）。抓到它的是包内端到端探针

   `proactive.identity_of()` 与 `IDENTITY_KEYS` 是唯一口径，构建端 `from minicode.proactive
   import identity_of`，并补一支**同时喂两侧**的针
   `test_the_two_sides_of_the_identity_use_one_projection`（反证：把构建端改回整份抄 →
   正好这一支红、其余 46 支照绿）+ 一支钉"非内容字段一律不许进身份"的

11. **补了一条本文没写的闸：「凭证要配得上本体」** —— §五 只写了"本机凭证与清单一致才跳过"，
   没写**凭证说的是不是眼前这台机器**。内核那份凭证在包的**根目录**、不在被排除的 `ms-playwright/`

如果馆藏库平均几个月才更新一次，路 1 现在这个样子就已经吃掉了绝大部分收益。

## 十、附：这些数是怎么量的（复量只要一条命令）

```
./.venv/Scripts/python.exe -X utf8 scripts/measure_package_size.py
```

只读（开 zip 中央目录 + 用 PyInstaller 自己的 `CArchiveReader` 开归档，不写不删不解压）。
分桶规则互斥、可对质：`/crawled/` → L3 馆藏；`ms-playwright` → L3 内核；
`_internal/frontend` → L1 前端；根上那两个 exe → L1 主程序；`使用说明.txt` → L1 手册；
其余全部 → L2。**脚本自己会校验"分桶合计 == zipfile 报的总数"，不等就直接退出 2** ——
一张对不上账的表比没有表更坏（它是拿来决定要不要动构建端的）。

它同时输出两个决策数：`L3 = 84.2%`（路 1 的收益上限）与
`minicode 1.68 MiB / 所在 exe 22.96 MiB = 7.3%`（**为什么必须先定"可替换单元"再谈 manifest**）。
换包复量用 `--zip` / `--exe` 指路径。

### Inno 那四件是怎么量的（复现配方，临时脚本已删）

`7zr`（精简版）**读不了 Inno**（`Cannot open the file as archive`），所以不是"解包"，
而是**用产品自己那份参数编变体**：复制 `packaging/gcode.iss`，**只改两处**
——`[Files]` 的 `Excludes:`（或换成显式几行 Source）、`OutputDir`/`OutputBaseFilename`；
`Compression=lzma2/max` 与 `SolidCompression=yes` **一个字都不许动**，否则四件之间不可比。

```
# 三个变体:排内核 / 排内核+馆藏 / 只装 L1
%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe /DAppVersion=<版本> packaging\_measure_*.iss
```

⚠ 两条当场踩到的坑，写下来免得下一轮重踩：① **别在 bash 里直接调 ISCC** —— MSYS 会把
`/DAppVersion=…` 当路径转换掉，报的是"只能有一个脚本文件"这种完全不相干的话；用
`subprocess.run([...])` 走 Python（`build_exe.py` 就是这么调的）。② `OutputDir` 是**相对
.iss 所在目录**的，`..\..\_tmp_delta` 会从 `packaging/` 一路跑到仓库外面去（第一次就写到
`D:\game\` 上了）；量完记得把产物收回 `_tmp_delta/` 并删掉外面那个空目录。
三件变体 exe（合计约 890 MB）与三个临时 `.iss` 都是**一次性量具，量完即删** ——
留在 `packaging/` 里迟早有人拿它编出发出去的包。
