# 改动审查视图与逐文件回退（对标 Qoder 的 Review 面板 / ZCode 的逐文件签核）· ①R1 已落地(v0.9.101),R2/R3 仍未开工

> 基线:`D:\game\mini-code` v0.9.99(`dab012c`)。本文件是"要不要做、怎么做"的决策依据,不是日程。
> 规矩:这一条动的是**用户与代码之间那层信任**(它改了什么、我认不认),按用户定的口径先出方案、
> 等拍板再动手。下面所有"现状"都是本轮逐行读出来的,每条带文件与行号,可以直接去核;
> 标了「动手前要核」的是本轮没读到确出处、不许当现状用的。

## 一、用户想要的是什么

一轮对话里学长写了 5 个文件。现在要知道"它到底改了什么"，只有两条路：
①点开每个文件自己看；②不满意就按「↶ 撤销」，一次退一步，退到哪一步全凭猜。
缺的是一个"本轮改动"视图：**列出改了哪几个文件 → 逐个看改了什么 → 只回退其中某一处**。
Qoder 把这层做成 Review 面板（并排 diff、逐文件接受/拒绝、编辑已发消息自动回滚工作区），
ZCode 把这层做成"破坏性改动必须人点头 + 会话分支安全试错"。

## 三、真正的缺口（三处，按风险从低到高）

### R1 · 「本轮改动」清单 + 逐文件回退（低风险，先做）
- 把 `_undo_stack` 从"只能弹"变成"能列"：`Agent.undo_records()` 返回
  `[{seq, path, display, kind: 改/新建, at}]`（**倒序给，最新在前**，与栈的语义一致）。
- 撤销不再只能"退一步"：`undo(seq=None)` —— 传 `seq` 就**只退那一条**，并从栈里摘掉它，
  比它更新的条目保持原样（同一文件被改两次时，退第 2 次不能把第 1 次的成果也吃掉）。
  这条口径必须写死并单独有测试，否则"逐文件回退"就是个新名字的乱序撤销。
- 不新增任何"记在哪里"的地方：审查视图读的就是 `_undo_stack`，**它一被清空（`/clear`、
  换会话、压过历史）视图就空**，界面必须照实说"这次会话里没有可退的改动"，不许留下
  一份"看起来还能退"的缓存。

### R2 · 逐文件的 diff 呈现（中风险，依赖 R1）
- 前像是字节全量，后像从磁盘现读 —— **读那一刻文件可能又被 bash/py_script 改过**
  （快照只管 `write_file`/`edit_file`，`agent.py:27` 那句注释明说 bash 的改动不在跟踪范围）。
  所以每个文件必须回一句"现在是这份内容，最后一次由我改动之前是这份"，
  并在"磁盘上这份和快照对不上"时**明说这一处可能被别的工具改过**，不许静默按前像 diff。
- diff 的规模要有盖：单文件超过 N KB 或跨度过大时给「前 200 行 + 另有 X 处未显示」，
  不许为了好看截掉中间还留着"完整 diff"这句话。
- 呈现只走一条通道：面板读后端算好的行，前端**不自己拼 diff 文案**（与 `_ask_trace_text`
  那条口径同一个理由：两处各拼一份就是两份真相，而且都摆在用户眼前）。

### R3 · "接受/回退这一轮"（高风险，排在最后，也可能永远不做）
- Qoder 那套"编辑已提交的消息 → 工作区文件自动回滚到那次对话前"是**同一层能力的另一面**，
  但它要求把"哪一批改动属于哪一条消息"记成一笔新账 —— 现在只有栈的顺序，没有回合边界。
- 加回合边界要付的账：`edit_resend` 那条链（已有"防副作用"断言的本质化要求）必须同时改，
  否则会出现"消息重发了，文件停在上一轮"。所以这一件**单独拍板，不许顺手做**。

## 四、必须写死的四条口径

1. **不假装覆盖 bash**。`bash` / `py_script` 改出来的东西不在快照里（`agent.py:27` 明说）。
   面板抬头必须写"只列我经 write_file / edit_file 改的文件；命令与脚本改的不在这里"，
   而不是让人以为"点全部回退就回到本轮开始前"。这是这一屏最危险的错觉。
2. **工作区外一律不出现**。快照走 `resolve_path(..., for_write=True)` 并被
   `PathOutsideWorkspace / PathBlocked` 挡掉（`:626`），所以栈里的路径天然安全；
   但展示时仍只给**相对工作区的路径**（与 `Attachment.to_dict`、`export_trace` 同一口径：
   绝对路径不出桥）。
3. **回退是动手面，要点头**：`/undo` 与逐文件回退都要过确认框，勾"不再询问"也不能把
   别人的改动吞回来 —— 回退前若该文件在快照之后又被改过，确认框必须写明这一点。
4. **撤销成功后话要说到位**：现在那句 `f"已撤销:{rec['display']} 已恢复为改动前的内容"`（`:360`）
   在"这是新建的文件"时其实说的是"删了它"。逐文件视图里 `kind` 要区分「恢复」与「删除」，
   回话也跟着分两种，别把删除说成恢复。

## 五、刻意不做 / 不要这样做

- **不做 git 集成式审查**（不在工作区偷偷 `git init`、不假设那是 git 仓库）：仓库的
  `worktree` 工具只跑 `list`/`status` 两条查事实命令、零写入（v0.9.99 P5 拍板过），
  审查视图同理只读快照，不碰 VCS。用户要提交走 `git-commit` 技能那条明路。
- **不做"文件树 + 逐行批注"式 IDE 体验**：那是另一个量级的界面工程，且这里的正当需求只是
  "看改了什么、退不退"。
- **不新增第三本改动账**（见 §二.5）：产出行、审查视图、撤销栈必须是同一份事实的三个视图；
  真要新落盘（例如把本轮改动写成 JSON 存档）就必须交"个人数据四处登记税"
  （`.gitignore` + `state_files.SHIP_NEVER` + `mydata.TABLE` + 打包清理），
  目前看不需要，别顺手加。
- **不许把"编辑消息即回滚工作区"当成第一版卖点**（R3 单独拍板）。

## 八、落地时补的账(v0.9.101,只做到 R1)

- **R1 的"漂移"那一半需要一个原稿没写的新东西**:光有前像判不出"我改过之后它又被动过",
  所以加了 `_mark_after_mutation` —— 写完那一刻 stat 一次(size+mtime)存进快照,`_drifted()`
  据此点名。**顺序是坑**:漂移必须在动手回退**之前**判,落盘之后再问,磁盘上就是我们写好的
  那份,提醒永远不成立(第一版正是这么写错的,`test_undo_records_flag_external_touch` 抓的)。
- **写失败的那一次不进清单**:`_snapshot_before_mutation` 先落一条、`_mark_after_mutation`
  认出 `is_failure` 就把它摘掉。退不动的行比少列一行更骗人。
- **入口没有加第 15 颗按钮**:并进 🛰 监控第 5 段「本轮改动」(`monitor.SECTIONS` 加 `changes`),
  数据跟着 `get_activity()` 的 `changes` 一起走 —— 少一次往返,也少一处"产出行说有 3 个文件、
  审查清单还空着"的对不齐。
- **R2(逐文件 diff)与 R3(编辑消息即回滚)没做**:R2 等 R1 真用起来之后再看要不要;
  R3 要新记"哪一批改动属于哪一条消息",按稿 §五 那条单独拍板。
