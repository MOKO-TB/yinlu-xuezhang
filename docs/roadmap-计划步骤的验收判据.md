## 一、要解决的问题

计划面板现在能告诉你的全是**意向**：第 3 步进行中、5 步做完了 2 步。
但"这一步真的做成了吗"没有任何判据 —— 标 `done` 的是模型自己说的一句话。

最扎心的是这件事**已经被写进代码注释**了：`planning.py:278` 在解释"子代理回来为什么不算一步做成"
时写着 ——「子代理回来的是**一段转述**,不是这一步做成的证据」。
它为此做的处理是：派活回来的那一步**不替主代理标 done**（v0.9.81 的口径）。
也就是说：作者看见了这个问题、选择了"不代标"，但**"什么才算证据"这一层始终没有做**。

现在这一步的完成判定链是：模型觉得做完了 → `plan(action=update, step=N, status=done)`
→ 状态写进 `plan.md` 的勾选标记（`STATUS_TO_MARK`，`planning.py:27`）→ 面板与对话卡照抄。
中间没有任何一件事被验证过。

## 二、已经具备的（别重做）

1. **步骤是有结构的**：`parse_plan()`（`:62`）产出 `{n, title, detail, status, done, depends_on, note}`，
   `depends_on` 已经支撑起 `ready_steps` / 可执行与卡住的调度视图（v0.9.81）——
   加一个字段是沿着现成的解析路走，不是另起一套。
2. **"写完后自动跑一次检查"这件事已经做过一次**：`agent._py_syntax_feedback()`
   （`agent.py:643` 附近）在 `write_file`/`edit_file` 落盘 `.py` 后立刻 `ast.parse`，
   不过就把行号与报错原文**回填进工具结果**让模型当场修。注释里点明是借鉴 aider 的
   lint-after-edit。这就是验收判据该长的样子：**结果进工具回话，不进会话留档的旁路**。
3. **命令执行有现成的口**：`bash` 工具 + 权限门 + 沙箱 + 后台任务三件套
   （`background` / `bash_status` / `bash_kill`），验收命令不必新写一个执行器。
4. **派活与计划的联动在**：`dispatch_text()` / `dispatch_start()` / `dispatch_end()`
   （`:224`、`:275`、`:313`）—— 验收失败要往哪儿写，那三条已经给了模式。

## 三、真正的缺口（三件，按风险排）

### V1 · 步骤带一条可选的验收命令（低风险，先做）
- `plan.md` 的步骤行支持可选的 `verify:` 备注（**跟着标题走，不新增文件、不加 front-matter 方言**），
  例：`- [ ] 修好登录跳转 —— verify: pytest -q tests/test_login.py`。
- 只有**模型自己填得出来**的才填（跑测试/跑构建/`--check`）。填不出就留空，
  **留空是正常态**，不许为了面板好看编一条 `true` 之类的空跑命令 —— 那是把"有验收"写成装饰。
- 硬规矩：**标 done 时若该步有 `verify` 且本轮没跑过，工具回话直接拒绝**，
  回话说清"这一步带验收命令，先跑它（或明确说不跑）"。这就是 `agent.py:27` 那套
  "不代标 done"的同一层克制，只是把依据从人眼换成一次执行。

### V2 · 验收真跑，并把结论写进三个视图（中风险，依赖 V1）
- 跑走 `bash` 那条路，因此**照旧受权限门与沙箱管**：验收命令该弹确认框就弹，
  绝不为"自动验收"开一条绕过确认的捷径（v0.9.87 白名单那条设计的核心不能被这里啃掉）。
- 结论落三处、且都从同一次执行派生：计划文件（`note` 里带 `verify ✓/✗ + 时刻`）、
  对话里的计划卡、右侧「任务监控 → 计划」段。**只准有一处真跑**，另两处读同一份状态。
- 失败的文案必须硬：「这一步的验收没通过（退出码 N，输出尾部如下），我没有把它标成完成」。
  **不允许"跑不过但看起来差不多"就 done**，也不允许把失败悄悄重写成 pending。
- 长验收（>2 分钟）走 `background=true`，然后按"这一步在等验收"显示，
  不许把主循环卡在那儿 —— 与 §2 v0.9.84~86、v0.9.91 那两条后台/进度口径一致。

### V3 · 目标级的完成判据（高风险，最后，也可能不做）
- ZCode 的 goal 模式是"把长活拆成可验证里程碑 + 自动校验进度"。V1+V2 做到的是
  **每步有判据**；再往上一层是"整轮目标有判据"（例如"全量测试绿 + 文档四处同步"才算目标达成）。
- 这一层要引入"目标"这个一等公民（现在只有 `goal` 是 `parse_plan()` 的一个字符串字段），
  并且要回答"目标没达成时算哪一步失败"。**没有真实使用反馈之前不做**。

## 四、必须写死的四条口径

1. **验收命令不是新权力**：它跑的权限与用户自己敲 `bash` 完全一致；带 `rm -rf`、
   敏感路径、外传形态的命令，**权限门先拦**，不因为"这是验收"就放行。红线在任何档位硬拒这条不变。
2. **一次验收只属于一步**：不给"全量跑一遍"的隐性放大。步骤多时逐个跑，
   或者明确让模型只对关键步设 `verify`（提示词里写死，别在代码里偷偷合并跑）。
3. **结果不进 KV 前缀**：验收输出回填进**这一次**工具结果，像 B0/B1 与后台状态那样
   "只搭请求、不进留档"，否则历史里全是同一条 pytest 尾巴，白占上下文还压不动。
4. **不许伪造时刻**：`verify ✓` 必须带这次执行的时刻；模型自己写"已验证"但没有跑过的记录
   一律视为无效（拒绝标 done），这是这一屏唯一有意义的硬闸。

## 五、刻意不做

  已经划掉过一次"LLM 当裁判"，理由没变 —— 裁判本身要证据，否则只是把转述换了个说法。
- **不做 CI**：`.github/workflows/ci.yml`（v0.9.89）已经是仓库级验收，那是"每次推送都跑"，
  与这一步的粒度不同，不要混。
- **不新增落盘文件**：验收状态挂在 `plan.md` 的 `note` 上。真要另开一份账就得交
  个人数据四处登记税，且会造出第二份真相 —— 现在不需要。
- **不改 `plan.md` 的既有方言**：四态标记 `- [ ] / [/] / [x] / [!]`（`:27`）与
  `failed` 语义保留；新字段只加在备注里，老文件照常解析（这一条要有回归针）。

## 八、落地时补的账(v0.9.101 做 V1;V2 由并行会话 9921095 接走)

- **"这一轮跑过没有"的那本账落在 `ctx.verify_runs`**(内存、30 条盖、不落盘),写账的地点
  在 `bash` handler 跑完那一刻 —— 不在 plan 里,也不在 Agent 里:那一层同时看得到命令、
  退出码与输出,而 plan 工具只该问"跑过没有"。
- **后台与超时不进账**:它们没有"退出码是几"这个结论。记进去等于给"跑过了"开门。
  代价照实说:一条真要跑 10 分钟的验收命令,现在只能前台等(V2 才接 `background=true`)。
- **严格整条相等才认**:`pytest -q x --tb=short` 不验 `pytest -q x`。放宽成"包含"就等于
  让模型自己决定什么算验过 —— 那正是这一件要治的病。
- **V2 由并行会话做掉了(9921095)**:命中的验收命令跑完那一刻把 `verify ✓/✗ + 时刻`写进该步备注(走 `_write_plan` 那一个落盘出口),计划卡与监控段读的都是 plan.md —— 正是本稿 §三.V2 定的「一次执行、三处视图读同一份状态」。**长验收走 `background=true` 那一半仍没做**(V1 的口径是后台不进账,那条路要连「这一步在等验收」的显示一起设计)。**V3(目标级判据)按稿继续不做** —— 没有真实使用反馈之前不做。
